# 搜索策略与查询构造指南

## 一、来源路由：按问题类型选择搜索目标

### 学术/科学问题

**优先级从高到低：**

1. **Google Scholar / Semantic Scholar**——最广泛的学术搜索入口，覆盖大部分英文期刊和会议论文
2. **PubMed / PubMed Central**——生物医学领域的权威数据库，医疗相关问题必查
3. **arXiv**——计算机科学、物理、数学的预印本，获取最前沿但未经同行评议的工作
4. **Crossref / OpenAlex**——用于验证 DOI、获取引用关系和归一化引用指标（FWCI）
5. **领域专门数据库**——心理学用 APA PsycINFO，社科用 JSTOR，化学用 SciFinder

**中文学术：**
- **CNKI（知网）**——中文学术论文最大数据库，硕博论文覆盖最全
- **万方 / 维普**——补充 CNKI 的覆盖盲区
- **注意**：CNKI 收录范围很广，收录不等于高质量。用北大核心/CSSCI/CSCD 目录判断期刊层次

### 工程/技术问题

**优先级从高到低：**

1. **官方文档**——任何技术问题的首选。注意版本匹配
2. **GitHub**——搜索代码实现、issue 讨论、README。用代码搜索找具体 API 用法
3. **RFC / IETF 文档**——网络协议和互联网标准的权威来源
4. **Stack Overflow**——实践经验丰富，但答案可能过时。优先看高赞 + 近期更新的答案
5. **技术博客**——InfoQ、The New Stack、个人技术博客。作者身份需逐个验证
6. **标准化组织**——NIST、ISO、W3C——涉及标准和合规时查

**中文工程：**
- **CSDN / 稀土掘金 / 知乎技术专栏**——质量参差不齐，逐篇判断
- **国标（GB）/ 行标**——中国特定的技术标准，全国标准信息公共服务平台可查

### 商业/市场问题

**优先级从高到低：**

1. **监管文件**——SEC EDGAR（美股财报）、企业年报、招股说明书——最不容易造假的数据来源
2. **行业研究机构**——Gartner、IDC、CB Insights、Frost & Sullivan——专业分析但需注意付费报告可能有倾向性
3. **财经媒体**——Bloomberg、Reuters、FT、WSJ——有编辑审核流程的一手报道
4. **行业协会报告**——覆盖特定行业的宏观数据
5. **企业官方信息**——投资者关系页、新闻稿——一手但有明显自我宣传倾向，需交叉验证

**中文商业：**
- **财新 / 界面 / 第一财经**——具有独立调查传统的财经媒体
- **国家统计局 / 行业主管部门公告**——官方统计数据
- **巨潮资讯网 / 上交所/深交所公告**——上市公司监管信息
- **注意区分**：独立调查报道 vs 企业通稿/软文。后者在中文财经媒体中比例很高

### 社区/用户声音

当研究涉及真实用户体验、产品口碑、非官方视角时：

- **Reddit**——英文社区讨论，按 subreddit 定位特定领域
- **知乎 / V2EX**——中文技术和泛知识社区
- **HackerNews**——技术创业领域的高质量讨论
- **产品评论区**——App Store、Google Play、G2、Capterra
- **行业论坛**——特定行业的专业社区

**使用社区数据的原则：** 用于发现问题和假设，不用于支撑事实结论。社区讨论反映真实体验但样本有偏、没有审核流程。

### 跨领域问题

当问题跨越多个领域（比如"某种 AI 药物发现技术的商业前景"），按子问题的领域分别路由：
- 技术原理 → 学术来源
- 工程实现 → 技术来源
- 市场前景 → 商业来源

不要用一种来源覆盖所有角度。

## 二、查询构造：如何写出高效的搜索词

### 通用原则

- **用领域术语而非日常用语**——"心肌梗死"而不是"心脏病发作"，"container orchestration"而不是"管理多个 Docker"
- **包含限定词**——时间范围（2024-2026）、地域（中国/美国/欧盟）、特定方法或技术
- **一次查一个子问题**——不要把整个研究问题塞进一条搜索词

### 按来源类型的查询技巧

**通用网络搜索（WebSearch）：**
- 使用自然语言 + 关键词组合
- 加 `site:` 限定特定网站（如 `site:nature.com`、`site:sec.gov`）
- 加时间限定词（如 `after:2024-01-01`）
- 中文查询和英文查询分开发，不要混用

**学术数据库：**
- 使用布尔算符：`"exact phrase" AND (term1 OR term2) NOT excluded_term`
- 用 MeSH 术语搜 PubMed（比自然语言更精准）
- 按引用数或日期排序，根据需要切换
- arXiv 按 category 过滤（cs.AI、cs.CL 等）

**GitHub：**
- 代码搜索：精确的函数名、API 名、错误信息
- Issue/Discussion 搜索：错误描述 + 关键词
- 用 `language:` 和 `stars:>100` 过滤

**监管/财务文件：**
- SEC EDGAR：用公司 CIK 号或 ticker 搜索，按表单类型过滤（10-K 年报、10-Q 季报、8-K 重大事件）
- 中国证监会/交易所：用公司代码搜索

### 多语言搜索

如果问题与中国相关，或者涉及中文学术文献：
- 同时用中文和英文搜索，结果分别收集
- 中文搜索词要考虑术语差异——同一个概念在中英文学术界可能用不同的名词
- 中国政策相关问题：搜中文来源（政府公告、政策原文），不依赖英文翻译

## 三、子问题拆解：从大问题到可搜索的小问题

### 拆解策略

把大问题拆成可以独立搜索的子问题（数量由覆盖度决定，不设上限）。每个子问题应该满足：
- **可独立回答**——不需要先回答其他子问题
- **可搜索**——知道去哪里搜、用什么词
- **有明确的"完成"标准**——知道什么算找到了答案

### 常见拆解维度

| 维度 | 适用场景 | 示例 |
|------|---------|------|
| 核心事实 | 所有问题 | "X 的定义/原理/现状是什么" |
| 历史演变 | 趋势分析 | "X 在过去 5 年如何发展" |
| 正面证据 | 论证类 | "支持 X 的证据有哪些" |
| 反面证据 | 论证类 | "反对 X 或 X 的局限性有哪些" |
| 对比基准 | 比较类 | "X 和 Y 在 Z 维度上如何比较" |
| 实践案例 | 工程/商业 | "谁在用 X？效果如何？" |
| 定量数据 | 需要数字 | "X 的市场规模/成功率/成本是多少" |
| 利益相关方观点 | 争议话题 | "不同立场的人怎么看 X" |

### 子问题检查

拆完后检查：
- 覆盖了用户关心的所有角度吗？
- 有没有包含反面/反对的角度？（容易遗漏）
- 子问题之间有没有明显重叠？（去重）
- 有没有内容高度相似的子问题？（合并重叠的，但不要为了"数量少"而强行合并本应独立搜索的维度）

## 四、搜索失败时的重构

### 判断"搜索失败"

- 首轮搜索返回的结果与子问题不相关（关键词命中但内容不对）
- 返回结果数量极少（该领域文献应该很多但搜不到——说明查询词可能不对）
- 所有结果来自低质量来源（找到了但没有可信的）

### 重构方法

按以下顺序尝试，每轮改一个维度：

**第 1 轮：换词**
- 用同义词或上下位词替换核心术语
- 尝试更专业或更通俗的表达
- 示例：`"autonomous driving safety"` → `"self-driving vehicle collision avoidance"`

**第 2 轮：调范围**
- 扩大：去掉限定词，搜索更广泛的类别
- 缩小：加更多限定词，聚焦到特定子领域
- 示例：扩大 `"CRISPR liver disease treatment"` → `"gene therapy liver disease"`

**第 3 轮：换语言或换来源**
- 中文搜不到试英文，反之亦然
- 学术数据库搜不到试通用搜索
- 正式文献搜不到试技术社区讨论

**所有合理的重构策略都已尝试后仍无结果** → 标记为"未找到充分证据"，在报告中如实说明搜索了什么、没找到什么。这本身是有价值的发现——说明该领域可能确实缺少公开研究。

### YMYL 特殊规则

YMYL 话题的搜索失败处理更保守：
- 不要因为搜不到就降低证据标准去引用低质量来源
- 明确告知用户"在 X 来源中未找到 Y 相关的高质量证据"
- 不用"假设性生成"（比如让模型猜测一个研究可能的结论）来填补空白
