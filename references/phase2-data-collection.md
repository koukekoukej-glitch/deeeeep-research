# Phase 2：数据收集

**目标**：产出一批经过初步分级的原始来源——覆盖用户问题的各个子问题，横跨相关领域。

**核心原则**：搜索的广度和精度取决于派对了人。按领域分工让每个子 Agent 用自己最擅长的方法搜自己最熟悉的地方，比一个通用 Agent 搜所有地方效果好得多。

**这一步的关键约束**：你不亲自搜索。你决定这个问题涉及哪些领域、派哪些子 Agent 去搜、给每个子 Agent 什么具体任务，然后收集和汇总结果。

---

## 工具与能力边界

- **WebSearch**——通用搜索，适合发现来源和获取广泛信息
- **WebFetch**——读取特定 URL 的内容，适合深入阅读已发现的来源
- **已知限制**：无法访问付费数据库（如付费学术期刊全文、Gartner 付费报告）。遇到付费墙时，尝试找公开摘要、预印本版本或替代来源

---

## 第一步：判断需要哪些领域

根据 Phase 1 拆出的子问题，判断每个子问题属于哪个领域。六个专业领域覆盖了绝大多数研究场景：

| 领域 | 覆盖什么 | 何时启用 |
|------|---------|---------|
| 英文学术 | 科学证据、临床研究、理论分析、学术综述 | 子问题需要学术论文或研究数据支撑 |
| 中文学术 | 中文期刊、中文学术生态、中国临床试验 | 子问题涉及中国学术研究或中文文献 |
| 英文工程 | 技术文档、开源项目、RFC 标准、技术社区 | 子问题涉及技术实现、框架选型、代码 |
| 中文工程 | 国标/行标、国内大厂技术博客、中文技术社区 | 子问题涉及国内技术生态或中文技术资料 |
| 英文商业 | SEC 监管文件、行业报告、财经媒体、事实核查 | 子问题涉及市场、商业模式、财务数据 |
| 中文商业 | A 股/港股披露、央媒政策、中文财经媒体 | 子问题涉及中国市场、政策、中文商业信息 |

**一个子问题可以同时派给多个领域。** 比如"X 药的安全性"同时需要英文学术（临床数据）和中文学术（中国临床试验）。

### 六个领域覆盖不到时怎么办

大多数问题都能被这六个领域覆盖——医疗走学术 + YMYL 标记，法律走商业 + YMYL 标记，政策走中文商业 + YMYL 标记。但有两种情况需要特殊处理：

| 情况 | 处理方式 |
|------|---------|
| 需要社区/用户声音（产品体验、用户痛点、市场口碑） | 在对应领域的子代理 prompt 里额外指定搜索 Reddit / 知乎 / HackerNews。社区数据不需要独立的子代理，但要明确告诉子代理：社区来源只能用于发现问题和假设，不能用于支撑结论。 |
| 问题完全超出六个领域（比如纯艺术鉴赏、个人情感咨询） | 告知用户："这个问题超出了我的系统化研究能力，我可以尝试搜索但无法保证覆盖度和权威性。" 用户同意后，用通用 WebSearch 直接搜索，报告中标注"未经领域专业方法论验证"。 |

## 第二步：拆分搜索方向并派出子代理

### 2a. 领域内按搜索方向拆分

第一步把子问题映射到了领域。现在看每个领域内部：如果某个领域分到了多个**搜索方向独立**的子问题，为每个独立方向各派一个子代理并行搜索，而不是让一个子代理串行处理该领域的所有子问题。

**独立方向**：两个子问题的搜索词几乎不重叠，找到的文献/文档大概率是不同的集合。例如"X 技术的算法原理"和"X 技术在 Y 行业的落地案例"——前者搜论文和技术文档，后者搜案例报告和行业分析，搜索路径完全不同，应该拆成两个子代理。

**同一方向**：两个子问题会命中大量相同的来源，或后一个依赖前一个的搜索结果。例如"X 的效果如何"和"X 的已知局限性"——同一篇论文往往既报告效果也讨论局限，放在一个子代理里更高效。

拆分后的并行度不再被六个领域封顶。例如英文学术领域分到 4 个独立方向 → 4 个英文学术子代理并行；中文工程领域只有 1 个方向 → 1 个子代理。总子代理数 = 所有领域的独立方向数之和。

### 2b. 派出子代理

用 Agent 工具为每个搜索方向 spawn 一个子代理。**在一条消息中同时发出所有 spawn 请求，让它们并行执行。**

每个子代理的 prompt 按以下结构写：

1. **读取方法论**——告诉子代理去读自己的方法论文档
2. **子问题列表**——明确说清要回答哪几个子问题
3. **YMYL 标记**——如果涉及 YMYL 话题，告知子代理采用更严格的证据标准
4. **失败重构规则**——首轮搜不到时换同义术语重试——每轮只改一个维度（换词 → 调范围 → 换语言/来源），连续两轮零结果且无新策略可试时标记为未找到
5. **输出要求**——按本子代理方法论文档「输出格式」节定义的字段表返回**结构化数据**。每条来源含 11 个字段（url / title / tier / key_quotes / summary / relevance_score / as_of_date / status / interest_conflict / fallback_condition + 领域专属字段如 citation / version_scope / content_type / core_index）。**key_quotes 必须是原文 verbatim、不是子 agent 改写的摘要**——主 agent 在 phase 2.5 会基于这些字段选 8-12 个 URL 全文深读、phase 4 直接引用 key_quotes 做原文证据，子 agent 改写后原文细节就丢了

| 领域 | 方法论文档 |

**示例 1：同一领域拆为多个方向（英文学术组）**

研究问题"AI Agent 的评估方法"拆出 4 个子问题映射到英文学术：
- 子问题 A：AI Agent 的主流评估框架有哪些？
- 子问题 B：AI Agent 的安全性评估方法有哪些？
- 子问题 C：AI Agent 在实际业务中的 ROI 衡量方法？
- 子问题 D：AI Agent 评估中的已知局限和开放问题？

判断：A 和 D 搜索路径高度重叠（同一篇 benchmark 论文既介绍框架也讨论局限）→ 合并为方向 1。B 的搜索词和来源与 A 明显不同（安全是独立子领域）→ 方向 2。C 涉及商业价值衡量，学术来源也不同 → 方向 3。

结果：英文学术领域派出 **3 个子代理**并行，而不是 1 个。

**方向 1 的子代理 prompt：**

"先读取 `references/agents/en-academic.md` 获取你的搜索方法论和权威判断标准。

你负责以下 2 个子问题的学术文献搜索：
1. AI Agent 的主流评估框架有哪些？（benchmark 套件、评估维度、代表性论文）
2. AI Agent 评估中的已知局限和开放问题？

首轮搜不到时换同义术语重试——每轮只改一个维度（换词 → 调范围 → 换语言/来源），连续两轮零结果且无新策略可试时标记为未找到。

对每条找到的信息按 `references/agents/en-academic.md` 的「输出格式」节定义的字段表返回**结构化数据**：url、title、tier（一手权威/强二手/灰色一手/聚合转述）、key_quotes（原文片段 verbatim 1-3 段）、summary（2-3 句概括）、relevance_score、as_of_date（关键数据实际时点）、status（confirmed/rumored/estimated/outdated）、interest_conflict、fallback_condition、citation。**key_quotes 必须是原文 verbatim、不是改写的摘要**——主 agent 写报告时需要直接引用原话。"

## 第三步：收集结果

所有子代理返回后，汇总各自的发现：

- **跨语言发现**——同一个议题的英文源和中文源都找到了，记录下来供 Phase 3 交叉验证
- **低质量警告**——某个领域的子代理返回的结果大部分是聚合转述或更差的来源，记录"该领域未找到高质量来源"，在报告中如实说明
- **覆盖度检查**——对照 Phase 1 的子问题列表，每个子问题是否都有至少一条来源覆盖？遗漏的子问题考虑补派子代理或用通用搜索补充

---

## 预算意识

来源数量由覆盖度决定——每个子问题至少有一条可用来源覆盖，核心结论至少有两个独立来源支撑。达到这个标准就够了，不需要为凑数继续搜；没达到就继续搜，不因为"已经搜了很多"就停手。

搜索进行中发现问题比预期复杂得多 → 告知用户，让用户决定是否继续深入。每完成 2-3 个子问题的搜索后，向用户简要汇报当前进展和初步发现方向。

完成 Phase 2 后 → 读取 `references/phase2.5-selective-deep-read.md` 开始选择性深读。
