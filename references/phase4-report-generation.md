# Phase 4：报告生成

**目标**：把分析结论转化为用户能一遍读懂、读完能做决策的报告。

**核心原则**：报告的价值不在于写了多少字，在于用户读完之后能做决策。同样的证据，给不同的人、回答不同的问题，报告的结构和详细程度应该不一样。写报告之前先回顾 Phase 1 确认的两个信息：用户要用结论做什么决策，以及他对这个领域了解多少。

**这一步的关键约束**：把证据翻译成用户的语言，让他不需要懂你的方法论也能判断结论是否可信。下面的结构、格式、标注方式是工具箱，不是清单——每份报告只用其中对该研究有意义的部分。如果去掉某个格式元素用户做决策的能力不会下降，就不加。

---

## 报告形式匹配用户需求

根据 Phase 1 确认的研究类型和用户偏好，选择对应的报告组织方式。不是每种研究都用同一个模板。

| 用户需要什么 | 报告怎么组织 | 核心特征 |
|---|---|---|
| **叙述性分析**（"帮我搞懂 X"）| 叙事为主，证据嵌入段落，结论从故事中自然浮现 | 适合对领域不熟悉的用户，需要背景铺垫 |
| **结构化摘要**（"给我关键结论"）| 要点 + 表格为主，每个结论带证据标注 | 适合有领域背景、要快速获取关键信息的用户 |
| **对比矩阵**（"X vs Y vs Z"）| 多维对比表 + 各维度分析 | 适合选型决策，用户需要在多个选项间做取舍 |
| **仅摘要**（"快速概览就行"）| 一页精简，只有核心结论和关键数据 | 适合时间有限或只需初步判断的用户 |
| **完整深度研究** | 全量结构：结论 + 详细分析 + 矛盾 + 待补研究 + 方法论 | 适合需要完整证据链的决策场景 |

如果 Phase 1 没有明确用户偏好，默认使用"完整深度研究"——宁可信息充分让用户自己筛，不要替用户砍掉他可能需要的内容。如果用户需求不完全匹配以上任何一种，根据需求的核心特征组合使用多种形式的元素。

**不同形式使用下面章节的不同子集**：

| 报告形式 | 报告结构 | 不确定性呈现 |
|---|---|---|
| 完整深度研究 | 全部五段 | 正文用词传达，不用独立注释段 |
| 结构化摘要 / 叙述性分析 / 对比矩阵 | 核心结论 + 详细分析必选，矛盾与不确定性、待补研究视证据情况选用 | 同上 |
| 仅摘要 | 只用核心结论 | 同上 |

## 报告结构

用户从上往下读一遍。最重要的信息放最前面。

### 报告元数据

每份报告开头标注：

```
研究深度：[快速核查 / 标准研究 / 深度研究]
来源数量：[N 个]
截至日期：[YYYY-MM-DD]
```

YMYL 话题加标：

```
话题类别：[医疗健康 / 法律 / 财务 / ...]
证据标准：保守模式（优先一手权威来源，不确定性显式标注）
```

### 五段结构

**1. 核心结论**

直接回答用户的问题，列出关键发现，每个带核心数据。结论是"证据不足"就在这里直说——不铺垫背景，用户已经知道自己问了什么。

**2. 详细分析（主体）**

按子问题或主题组织。每个发现包含：结论陈述（一句话）→ 证据支撑（具体数据 + 引用 [N]）→ 证据质量标注。

报告的篇幅应如实反映研究的规模和复杂度——收集到 30 条证据的研究不应该和收集到 5 条证据的研究写出一样短的报告。每个发现写到把证据链交代清楚为止，不设字数上限。简单事实一段即可，复杂分析需要多少段就用多少段。

**3. 矛盾与不确定性**

主动呈现不同来源之间的冲突点、证据薄弱的领域、分析中做了什么假设。这一节让报告更可信——用户信任"这些我确定、那些我不确定"，不信任"一切都很确定"。

**4. 有待补研究**

用户问的问题中没能回答的部分、证据不足无法下结论的领域、如果想深入应该去查什么来源。

**这一节和正面结论享有同等的呈现地位**——独立成段，不是附录、不是脚注、不是塞在角落里的小字。告诉用户"什么我没查清楚"和"什么我查清楚了"一样重要——前者帮他避免基于不完整信息做决策。

**5. 参考来源**

完整引用列表。每条包含：作者/机构、标题、发布日期、URL、检索日期。格式：`[N] 作者/机构 (年份). "标题". 出版物. URL (检索日期: YYYY-MM-DD)`

## 不确定性的呈现

不确定性通过正文用词自然传达，不要用独立的"证据确定性"段落或括注打断阅读流。

### 正文内精确用词

在正文句子里，用精确的动词表达确定性程度：

| 确定性 | 中文用词 |
|--------|---------|
| 高 | 证实 / 表明 / 确定 |
| 中 | 提示 / 显示 / 指向 |
| 低 | 可能 / 似乎 / 与...一致 |
| 极低 | 推测 / 不能排除 |

NEVER 在每个章节末尾添加独立的"（证据确定性：X）"括注段落。这不是正常报告的写法——不确定性应该融入正文措辞中，让读者从动词就能判断结论的可靠程度。

### 证据断层处理

当某个结论的证据存在明显断层时，在该段落内说明三件事（不要单独成段）：具体缺什么、为什么缺、下一步去哪里找。

### YMYL 场景附加

仅在 YMYL 场景下，对直接涉及人身/财务/法律安全的关键结论，可在结论后用一句话补充证据基础（如"基于 1 项 II 期临床试验，样本量 120 人 [3]"），但不要用括注格式，融入正文。

## 负面结论的呈现

"没找到证据"是有价值的发现，不是报告的失败。调研发现现有的 5 个 Deep Research 产品（OpenAI、Perplexity、Elicit、Claude Research、Consensus）没有一家在产品中明确做"找不到就说找不到"的功能——这恰恰是差异化价值。

### 四条规则

**规则 1：独立段落，视觉权重相当。** 负面结论不塞进脚注、不缩进。它和正面结论在报告中占有同等位置。

**规则 2：说清缺什么、为什么缺。**

- 好："未找到 X 药物在 65 岁以上人群中的安全性数据。可能的原因：该药物 2023 年才获批，III 期试验排除了 65 岁以上受试者 [4]。"
- 坏："关于 X 药物在老年人群中的安全性，有待进一步研究。"

**规则 3：说明下一步。** 告诉用户如果想要更确定的答案，可以去哪里找、等什么。

**规则 4：YMYL 的精确措辞。** 负面结论精确到具体维度——"安全性维度：目前证据不足以支持结论。有效性维度：2 项 II 期试验显示积极信号，但样本量不足以确定。"不用"有待进一步研究"。

**平衡约束**：负面结论的总篇幅不应超过正面结论。如果一份报告的负面发现数量远超正面发现，先检查原因：是研究范围太宽导致大部分子问题超出搜索能力，还是证据确实普遍不足。前者应在核心结论中建议用户缩窄研究范围，而不是逐一展开每个负面发现。

### 措辞归因

来自 Santesso 2020 的实证（190 人样本测试）：

- 用"证据对 X 不确定"（80% 接受度），不用"我们对 X 不确定"（37% 接受度）
- 把不确定性归因于证据本身，不是归因于报告作者的能力

## 写作纪律

### 精确性

- **具体数字 > 模糊量词**：`"5 项 RCT（共 1,847 人）"` 而不是 `"多项研究"`
- **精确引用 > 泛泛归因**：`"WHO 2024 年指南 [3] 建议..."` 而不是 `"有专家建议..."`
- **明确时间 > 相对时间**：`"2024 年 Q3"` 而不是 `"最近"`
- **定量结果带统计**：`"下降 23%（95% CI: 18-28%, p<0.01）"` 而不是 `"显著下降"`

### 诚实性

- **承认不知道**：`"该领域目前没有找到公开的对比数据"` 而不是 `"进一步研究可能揭示..."`
- **区分事实与推断**：事实用陈述句 + 引用；推断用 `"这可能意味着..."` 并标注
- **区分相关与因果**：不把相关性表述成因果性
- **标注利益关系**：`"该结论来自 [公司 X] 资助的研究 [5]，需注意潜在利益冲突"`

### 表达效率

- **先结论后解释**——不铺垫，但证据链的完整性优先于篇幅——交代清楚证据比少写一段更重要
- **删掉不增加信息量的词**——"值得注意的是""有趣的是""众所周知"
- **每段一个核心观点**
- **适度使用表格**——对比多个选项时，表格比段落更直观

### 反信任侵蚀

以下措辞看似谦虚，实际上会侵蚀用户对报告的信任。禁止使用：

- "以上内容可能已过时"——标注截至日期让用户自己判断，不替他做判断
- "仅供参考，不构成任何建议"——如果证据充分就给建议，如果不充分就说证据不足，不用免责声明逃避
- "我们会持续更新"——你做不到持续更新，不做空头承诺
- "本研究全面调研了……"——空泛的自我肯定，删掉

## 中文报告的特殊适配

中文和英文的阅读习惯不同，报告需要针对性调整。

**并列论点用分项编号。** 中文段落里 3 个及以上的并列陈述容易被跳读——读者扫一眼就跳到下一段。用编号（1. 2. 3.）强制逐项对齐。2 个及以下的并列项可用段落行文，不需要编号。这来自腾讯较真等中文事实核查平台的实践。

**"弱推荐"必须加括注。** 中文语境中"弱推荐"容易被误读为"这个建议不太行"。必须在后面加括注说明——"条件性推荐（证据确定性低：仅基于观察性研究，尚无随机对照试验验证）"。

**涉及中国药品审评时用 CDE 三元判据。** 如果研究涉及中国境内药品上市审评，负面结论按"安全性 / 有效性 / 质量可控性"三个维度分别陈述，这是中国药品审评中心（CDE）的标准审评维度。其他医疗场景根据具体问题选择合适的分析维度。

**英文原文证据保留原文。** 引用英文来源的关键证据时，保留英文原文并附中文翻译对照，不只给翻译版——用户可能需要看原文判断翻译是否准确。

---

## 时效性标注

- **报告开头**标注"截至 YYYY-MM-DD"
- **时效敏感结论**在段落末标注数据日期："（数据截至 2025-Q3 [5]）"
- **不写"可能已过时"**——标注日期让用户自己判断
- **监管/政策类信息**标注具体的文件编号和发布日期

---

## 引用纪律

- **引用跟事实走**——强主张（定价数字、版本号、技术规格、原文引语）在句中事实后紧跟 `[N]`；通用论述、综合判断在段末统一收尾 `[1][2][3]`
- **多源必须独立角标** `[1][2][3]`。NEVER 写成 `[1,2,3]`、`[1-3]`、`[1、2、3]`——viewer 正则只匹配单个数字方括号
- **角标在句号前**：`陈述 [3]。` 引语角标在右引号外：`"原文" [3]`
- **引用即可查**——正文中每个 [N] 在 sources.json 中有完整条目
- **零容忍**——不允许占位符（`[?]`）、编号跳跃
- NEVER 根据记忆或推测编造 URL、DOI、论文标题。搜索不到就标注"未能找到原始来源"，不伪造引用
- NEVER 在正文中直接写裸 URL（如 `example.com/path`）。viewer 的 `linkify` 会把它转成可点击链接，和旁边的引用角标视觉混淆。所有 URL 一律放在 sources.json 中，正文只用 `[N]` 角标指向它

## 渐进生成策略

报告按章节（H2 段落）渐进生成，写完一个章节再写下一个。每个章节写完后校验该章节内的引用编号是否在 sources.json 中有对应条目，发现缺失立即补上。不设章节字数上限。

---

## Viewer 格式契约（硬约束）

报告由配套 viewer 网页渲染。以下规则对应 viewer 的解析逻辑，违反会导致渲染失败或视觉混乱。标杆样本见 `reports/ai-coding-agent-comparison-2026-04.md`。

### 文档骨架

1. 唯一一个 `# H1` 是报告标题。
2. 标题后紧跟 metadata 引用块，**只允许以下两个字段，不允许添加任何其他字段**：
   ```
   > 来源数量：{N} 个
   >
   > 截至日期：{YYYY-MM-DD}
   ```
   两个字段之间必须有一个空的 `>` 行，确保 viewer 渲染时各占一行。
   NEVER 添加"研究深度""研究范围""研究主题""评估总览"等额外字段。
3. `## TL;DR` 必须是正文第一个 H2。
4. 后续 `##` 章节按内容自然组织。**禁止**在标题中带手工编号（如 `§1`、`一、`、`1.`）——viewer 的 TOC 自动从 H2/H3/H4 抽取目录。
5. H2 章节名直接描述内容，不用中英混杂术语。
6. markdown 末尾**不写**引用来源列表——viewer 从 `sources.json` 自动渲染底部"引用来源"区。
7. **禁止**文档末尾的"自我标识"括号行。

### sources.json

与报告同名的 `.sources.json` 文件并列输出到 `reports/` 目录。viewer 从中读取来源数据渲染弹窗和底部引用列表。

**文件结构必须是**：`{"sources": [...]}` —— 一个对象，`sources` 键包含来源数组。NEVER 输出裸数组 `[...]`。

**viewer 强契约字段（6 个，全部必需）**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `num` | int | 与正文 `[N]` 严格对齐，连续编号从 1 开始 |
| `title` | string | 来源标题 |
| `url` | string | 完整 URL |
| `date` | string | `YYYY-MM-DD` 或 `YYYY-MM` |
| `authority_tier` | string | `T1` / `T2` / `T3` |
| `evidence_quote` | string | ≤200 字原文摘录 |

**一致性硬约束**：正文每个 `[N]` 必须在 sources.json 有对应条目，反之亦然。

**降级方案**：如果 sources.json 因故无法生成，在 markdown 末尾增加 `## 引用来源` 章节，按 `[N] 标题, URL, 日期` 格式逐条列出。

### 标点纪律

- 句号、逗号、顿号正常使用。**禁止**用 `·`（中点）替代标点。
- `·` 只允许两处：标题分隔（`AI Coding Agent · 2026 年 4 月`）、并列实体（`Cursor · Claude Code · Cline`）。

### 报告交付流程

报告完成后必须严格执行以下步骤，不可跳过。

**步骤 1 · 命名与写入**

报告文件名：`{主题关键词}-{YYYY-MM}.md`（全小写、连字符分隔、英文）。
来源文件名：与报告同名但后缀为 `.sources.json`。
两个文件都写入 `reports/` 目录。

**步骤 2 · 程序化格式验证**

报告和 sources.json 写入后，运行验证脚本：

```bash
py viewer/validate_report.py reports/{文件名}.md
```

脚本检查：metadata 字段是否只有规定的两个、H1 是否唯一、第一个 H2 是否为 TL;DR、标题是否有手工编号、角标格式是否正确（禁止逗号/连字符连写）、正文是否有裸 URL、sources.json 格式是否为 `{"sources": [...]}`、6 个必需字段是否齐全、正文角标和 sources.json 编号是否一一对应。

脚本输出"OK 格式验证通过"才能进入步骤 3。输出错误则按错误提示逐项修正，修正后重新运行脚本，直到通过。

**步骤 3 · 环境检测 + 交付链接**

交付链接前，先确认 viewer 服务在跑：

```bash
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8765/viewer/
```

- 返回 `200` → 服务正常，直接进入交付
- 返回其他或不可达 → 用 `py` 命令启动服务：
  ```bash
  cd viewer && py serve.py &>/dev/null &
  ```
  等待 3 秒后重新检测。最多重试 3 次（每次间隔 3 秒）。3 次后仍不通过 → 向用户报告"viewer 服务启动失败"，同时附上报告文件路径让用户手动查看。

环境就绪后，向用户输出以下两行（每次都必须输出，格式固定）：

```
报告文件：file:///reports/{文件名}.md
在线查看：http://127.0.0.1:8765/viewer/?report={文件名不含.md}
```

NEVER 省略这两个链接。NEVER 只给其中一个。这是用户判断报告是否成功入库的唯一凭据。
NEVER 输出"服务可能未启动"之类的猜测——要么确认服务在跑，要么自己启动它。
