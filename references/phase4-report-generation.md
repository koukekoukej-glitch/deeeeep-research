# Phase 4：报告生成

**目标**：把分析结论转化为用户能一遍读懂、读完能做决策的报告。

**核心原则**：报告的价值不在于写了多少字，在于用户读完之后能做决策。同样的证据，给不同的人、回答不同的问题，报告的结构和详细程度应该不一样。写报告之前先回顾 Phase 1 确认的两个信息：用户要用结论做什么决策，以及他对这个领域了解多少。

**这一步的关键约束**：把证据翻译成用户的语言，让他不需要懂你的方法论也能判断结论是否可信。下面的结构、格式、标注方式是工具箱，不是清单——每份报告只用其中对该研究有意义的部分。如果去掉某个格式元素用户做决策的能力不会下降，就不加。

---

## 报告形式匹配用户需求

根据 Phase 1 确认的研究类型和用户偏好，选择对应的报告组织方式。不是每种研究都用同一个模板。

| 用户需要什么 | 报告怎么组织 | 核心特征 |
|---|---|---|
| **叙述性分析**（"帮我搞懂 X"）| 叙事为主，证据嵌入段落，结论从故事中自然浮现 | 适合对领域不熟悉的用户，需要背景铺垫 |
| **结构化摘要**（"给我关键结论"）| 要点 + 表格为主，每个结论带证据标注 | 适合有领域背景、要快速获取关键信息的用户 |
| **对比矩阵**（"X vs Y vs Z"）| 多维对比表 + 各维度分析 | 适合选型决策，用户需要在多个选项间做取舍 |
| **仅摘要**（"快速概览就行"）| 一页精简，只有核心结论和关键数据 | 适合时间有限或只需初步判断的用户 |
| **完整深度研究** | 全量六段：核心结论 + 关键假设与翻盘条件 + 详细分析 + 矛盾不确定性与未覆盖维度 + 主线复述与回扣 + 参考来源 | 适合需要完整证据链的决策场景 |

如果 Phase 1 没有明确用户偏好，默认使用"完整深度研究"——宁可信息充分让用户自己筛，不要替用户砍掉他可能需要的内容。如果用户需求不完全匹配以上任何一种，根据需求的核心特征组合使用多种形式的元素。

**不同形式使用下面章节的不同子集**：

| 报告形式 | 报告结构 | 不确定性呈现 |
|---|---|---|
| 完整深度研究 | 全部六段 | 正文用词传达，不用独立注释段 |
| 结构化摘要 / 叙述性分析 / 对比矩阵 | 核心结论 + 详细分析必选，矛盾不确定性与未覆盖维度视证据情况选用，主线复述与回扣即使在短形式下也应保留（哪怕只有一句话）。关键假设与翻盘条件默认不保留、仅在 phase 1 用户明确要求时加 | 同上 |
| 仅摘要 | 只用核心结论 | 同上 |

## 报告结构

用户从上往下读一遍。最重要的信息放最前面。

### 报告元数据

每份报告开头标注：

```
研究深度：[快速核查 / 标准研究 / 深度研究]
来源数量：[N 个]
截至日期：[YYYY-MM-DD]
```

YMYL 话题加标：

```
话题类别：[医疗健康 / 法律 / 财务 / ...]
证据标准：保守模式（优先一手权威来源，不确定性显式标注）
```

**grounding 强度可选标注**（phase 3.5 已运行的报告必带；未运行 phase 3.5 的报告省略此字段）：

```
grounding 强度：N 条强核查项｜M 条 multi-source｜S 条 single-source｜U 条 [unverified]｜占比 P%
```

字段含义：N = 报告中所有强核查项总数（来自 `claims.json` 条目数）；M / S = NLI 判断为 `multi-source` / `single-source` 的数量；U = `mark_unverified` 降级数量；P = U/N 百分比。这一行让读者一眼看到本报告的判断有多少是"被独立来源 entail"、多少只是"单源待核"、多少是"未核但保留信息"——是判断报告可信度的速查指标。

### 六段结构

**1. 核心结论**

直接回答用户的问题，列出关键发现，每个带核心数据。结论是"证据不足"就在这里直说——不铺垫背景，用户已经知道自己问了什么。

**2. 关键假设与翻盘条件**

把研究判断站在的几个前提显式列出来——给读者一份"如果哪条假设错了、整套判断会怎么变"的可监控清单。

每条按以下结构呈现：

- **假设 N**：本研究的核心判断依赖于「{某个具体前提}」。
- **翻盘条件**：如果{该前提的具体反面情况}，{核心结论中的某条具体判断}就需要修正为{什么样}。
- **对冲**（可选）：研究中已经为这种情况做了什么准备（如"如果发现 X、则降级处理为 Y"）。如果没做就略过。

**这一段不是免责声明、是监控清单**——读者读完报告之后、可以拿这几条假设回去对照实际情况、自己判断本研究的结论什么时候开始失效。结尾「主线复述与回扣」段最后一句"如果主线错了、最可能错在哪个假设上"是这段的指针、本段是指针指向的清单本身。

**实操约束**：

- 完整深度研究列 3-5 条关键假设。多于 5 条要合并、少于 3 条很可能是没把假设挖出来
- 假设必须是"研究范围之内、但被作者选择相信而没继续往下查"的那些前提——不是"理论上一切都可能错"那种泛泛挂免责
- 翻盘条件必须具体到一条核心结论怎么变。不写"如果 X 不成立、结论可能要修改"、写"如果 X 不成立、则核心结论第 2 条「Y 应选 Z 方案」要改为「Y 应选 W 方案」"
- 短形式报告（结构化摘要 / 对比矩阵 / 仅摘要）默认省略本段——这段是为完整深度研究的读者准备的监控工具

**3. 详细分析（主体）**

按子问题或主题组织。每个发现包含：结论陈述（一句话）→ 证据支撑（具体数据 + 引用 [N]）→ 证据质量标注。

报告的篇幅应如实反映研究的规模和复杂度——收集到 30 条证据的研究不应该和收集到 5 条证据的研究写出一样短的报告。每个发现写到把证据链交代清楚为止，不设字数上限。简单事实一段即可，复杂分析需要多少段就用多少段。

**4. 矛盾、不确定性与未覆盖维度**

三件事合在同一段呈现：

- **证据冲突**：不同来源对同一问题的不同结论、各自的依据、判断哪一方更可信的理由
- **证据薄弱处**：分析中做了什么假设、假设建立在多少证据上、哪些结论对假设的敏感度高（这一条和第 2 段「关键假设与翻盘条件」的关系：第 2 段列**判断站在的前提**及其翻盘条件，是给读者的监控清单；本条说**这些前提建立在多少证据上**，是衡量监控清单本身的可靠度。两段互补、不重复）
- **未覆盖维度**：用户问题中本研究**主动选择不深入**的部分、为什么不深入（搜索能力 / 范围 / 时点限制）、想深入应该去查什么来源

**这三件事和正面结论享有同等的呈现地位**——告诉用户"研究的边界画在哪里"和"研究覆盖到的部分"一样重要、前者帮他避免基于不完整信息做决策。

但**呈现位置上禁止把"未覆盖维度"塞到报告末尾作为独立结尾段**——那种结构会让读者最后一眼看到的是"我没查到 / 没查清"，整份报告退化成道歉式收尾。三件事合在中段（紧跟「详细分析」之后），结尾留给「主线复述与回扣」做 punchline 收束。

**5. 主线复述与回扣**

报告结尾、用一段话（控制在 200 字以内）做以下三件事——**所有三件事的具体内容来自 `report_thesis.json`、不允许 LLM 临场重新组织主线**：

1. 把 `punchline`（来自 report_thesis.json 同名字段）**原文**再说一遍——加深读者记忆。这是 punchline 在报告中第二次出现（第一次在「核心结论」开头）
2. 把 `decision_action`（来自 report_thesis.json 同名字段、对应 user_profile.json 的 decision_context）作为最后一句——告诉读者具体该做什么、什么时间做、什么条件验证
3. 把 `fallback_pivot`（来自 report_thesis.json 同名字段）作为倒数第二句——指出"如果这个主线错了、最可能错在哪个监控信号上"。完整假设清单在第 2 段「关键假设与翻盘条件」

这一段**禁止**写"待补研究"、"未来工作"、"持续关注"——那些已经在第 4 段说过了。结尾留给读者带走的是三件东西：punchline 印象 + decision_action 具体动作 + fallback_pivot 监控信号。

**6. 参考来源**

完整引用列表，按 num 升序排列。每条用 `[N] {标题} — {YYYY-MM-DD} — {T1/T2/T3} — {URL}` 格式独立成行，字段间用全角破折号 `—` 分隔。详细约束见下文「Viewer 格式契约」第 6 条——markdown 自带这段是硬性要求（保证脱离 viewer 也自洽），viewer 渲染时会自动移除并用 sources.json 富展示版本替代。

## 不确定性的呈现

不确定性通过正文用词自然传达，不要用独立的"证据确定性"段落或括注打断阅读流。

### 正文内精确用词

在正文句子里，用精确的动词表达确定性程度：

| 确定性 | 中文用词 |
|--------|---------|
| 高 | 证实 / 表明 / 确定 |
| 中 | 提示 / 显示 / 指向 |
| 低 | 可能 / 似乎 / 与...一致 |
| 极低 | 推测 / 不能排除 |

NEVER 在每个章节末尾添加独立的"（证据确定性：X）"括注段落。这不是正常报告的写法——不确定性应该融入正文措辞中，让读者从动词就能判断结论的可靠程度。

### 证据断层处理

当某个结论的证据存在明显断层时，在该段落内说明三件事（不要单独成段）：具体缺什么、为什么缺、下一步去哪里找。

### YMYL 场景附加

仅在 YMYL 场景下，对直接涉及人身/财务/法律安全的关键结论，可在结论后用一句话补充证据基础（如"基于 1 项 II 期临床试验，样本量 120 人 [3]"），但不要用括注格式，融入正文。

## 负面结论的呈现

"没找到证据"是有价值的发现，不是报告的失败。调研发现现有的 5 个 Deep Research 产品（OpenAI、Perplexity、Elicit、Claude Research、Consensus）没有一家在产品中明确做"找不到就说找不到"的功能——这恰恰是差异化价值。

### 四条规则

**规则 1：独立段落，视觉权重相当。** 负面结论不塞进脚注、不缩进。它和正面结论在报告中占有同等位置。

**规则 2：说清缺什么、为什么缺。**

- 好："未找到 X 药物在 65 岁以上人群中的安全性数据。可能的原因：该药物 2023 年才获批，III 期试验排除了 65 岁以上受试者 [4]。"
- 坏："关于 X 药物在老年人群中的安全性，有待进一步研究。"

**规则 3：说明下一步。** 告诉用户如果想要更确定的答案，可以去哪里找、等什么。

**规则 4：YMYL 的精确措辞。** 负面结论精确到具体维度——"安全性维度：目前证据不足以支持结论。有效性维度：2 项 II 期试验显示积极信号，但样本量不足以确定。"不用"有待进一步研究"。

**平衡约束**：负面结论的总篇幅不应超过正面结论。如果一份报告的负面发现数量远超正面发现，先检查原因：是研究范围太宽导致大部分子问题超出搜索能力，还是证据确实普遍不足。前者应在核心结论中建议用户缩窄研究范围，而不是逐一展开每个负面发现。

### 措辞归因

来自 Santesso 2020 的实证（190 人样本测试）：

- 用"证据对 X 不确定"（80% 接受度），不用"我们对 X 不确定"（37% 接受度）
- 把不确定性归因于证据本身，不是归因于报告作者的能力

## 写作纪律

### 精确性

- **具体数字 > 模糊量词**：`"5 项 RCT（共 1,847 人）"` 而不是 `"多项研究"`
- **精确引用 > 泛泛归因**：`"WHO 2024 年指南 [3] 建议..."` 而不是 `"有专家建议..."`
- **明确时间 > 相对时间**：`"2024 年 Q3"` 而不是 `"最近"`
- **定量结果带统计**：`"下降 23%（95% CI: 18-28%, p<0.01）"` 而不是 `"显著下降"`

### 数据翻译规则（每个数字背后的"所以"）

**报告里出现的每个数字 / 事实、必须紧跟一句"所以"——告诉读者这个数字意味着什么、对决策有什么用。** 写不出"所以"的数字直接删掉——它对读者没价值、占位置又稀释信号。

读者读到「Harvey AI 估值 110 亿美元」时、会立刻问"所以呢、这是高还是低、和谁比、对我的判断意味着什么"。报告必须替他回答这一问、否则数字就是数据库导出、不是判断。

**实操**：

- 数字后面紧跟解释句、用"所以 / 这意味着 / 相当于 / 比 X 高 Y 倍"等连接词。例：「Harvey AI 估值 110 亿美元（一年内翻 2.2 倍）——这个估值已经接近第一梯队 SaaS 公司（Snowflake 上市时约 700 亿、ServiceNow 同期约 1500 亿），但产品成熟度还差一个量级、所以这个估值是对未来 3-5 年法律科技市场的看涨期权、不是对当前营收的合理定价」
- 一句话写不完"所以"、说明这个数字承载了一段判断——把那段判断写出来、单独成段
- 真的就是背景信息（如"全球 GDP 约 100 万亿美元"）、问问自己读者是不是已经知道——是的话删掉

**自检**：写完一段、把段里的每个数字 / 比例 / 日期 / 事实圈出来、对每个问"如果删掉这条事实、报告的判断会不会变弱？"不会变弱的、删。

**例外**：参考来源段、矛盾、不确定性段——这些段的数字本身就是"备查信号"、不需要每个都跟"所以"。

### 诚实性

- **承认不知道**：`"该领域目前没有找到公开的对比数据"` 而不是 `"进一步研究可能揭示..."`
- **区分事实与推断**：事实用陈述句 + 引用；推断用 `"这可能意味着..."` 并标注
- **区分相关与因果**：不把相关性表述成因果性
- **标注利益关系**：`"该结论来自 [公司 X] 资助的研究 [5]，需注意潜在利益冲突"`

### 显式排序判断

**完整深度研究的核心结论 / 关键假设 / 详细分析三段、必须出现至少 3 处显式排序判断**——例如"最关键变量"、"最被低估的角色"、"最有可能翻盘的假设"、"风险最大的环节"、"最先该看的指标"。这些排序判断是把"研究做完了"和"研究有判断"区分开的边界。

**显式排序的反面是中性陈列**——把 5 个候选方案、3 个风险因素、4 个利益相关方平均铺开、不告诉读者"哪个最重要"。中性陈列读起来公允、读完没法做决策。

**实操**：

- 把"X 机构指出 / 业内分析人士认为 / 有研究表明"换成"我认为 / 这份研究的判断是 / 据现有证据、最可能的解释是" + 显式归因。归因可以中立（"这个判断主要基于来源 [3] 的实证、其他来源仅作交叉验证"）、但**判断的主体必须是报告作者、不是匿名第三方**
- 每列出 3+ 个并列项时、说明你认为哪一个最重要、为什么。例：列出 5 个 AI 编程工具、不要平均介绍——告诉读者哪个适合"日常代码补全"、哪个适合"复杂重构"、哪个最被低估
- 如果研究真的没有排序判断（5 个方案对你的场景同等适用）、明确说"在你描述的场景下这 5 个方案差异不大、选哪个主要看团队偏好"——这也是一个判断、不是中性陈列

**为什么强制至少 3 处**：少于 3 处、报告退化为"信息汇编型"——读者得到的是"市场上有 X / Y / Z"、不是"我建议你做 X"。3 处是"判断密度"的下限——核心结论 1 处 + 详细分析 2 处即可达成。

**自检**：报告写完、ctrl+F 搜"最 / 首先 / 优先 / 关键 / 最重要 / 应该 / 建议"——找到的位置数 ≥ 3 才算达标。少于 3 处、说明研究做完了但作者没出场、回去补判断。

### 表达效率

- **先结论后解释**——不铺垫，但证据链的完整性优先于篇幅——交代清楚证据比少写一段更重要
- **删掉不增加信息量的词**——"值得注意的是""有趣的是""众所周知"
- **每段一个核心观点**
- **适度使用表格**——对比多个选项时，表格比段落更直观

### 读物感操作清单（让报告读起来像有人在跟你说话）

报告是写给读者读的、不是给数据库塞的。**读起来像有人在跟你说话**——这是 deep research 区别于维基百科条目的地方。

**作者声音**：

- 报告里有明确的"我"——"我认为"、"这份研究的判断是"、"我对这个估值的看法"。不是每段都要"我"、但通篇看下来读者要能感受到背后有一个具体的判断者
- 不要把所有结论都归给外部主体（"研究表明"、"数据显示"、"专家认为"）——这种写法在论文里合规、在判断交付型报告里是逃避
- 表达不确定时、说"我不确定 X、因为 Y"、不说"该领域尚需进一步研究"——前者是承认、后者是模板

**节奏起伏**：

- 长短句交替——一段全长句、读起来像论文；一段全短句、读起来像微博。混着用
- 关键判断单独成段、不要塞在长段中间。例：核心结论里"我建议你选 X"独立成行、视觉上突出
- 不要每段都从"首先 / 其次 / 此外"开始——这种连接词暴露 AI 模板。直接进入新论点

**对话感**：

- 在合适的位置直接对读者说话——"你可能会问、为什么 X 比 Y 重要、这是因为..." / "如果你的场景是 A、跳过下一段；如果是 B、重点看这里"
- 把读者可能的反驳替他说出来、再回应——"你可能会觉得 110 亿估值太高、确实、但..." 这种"反驳-回应"对话比平铺直叙更有说服力
- 重要数据后给一个具体场景——"这个延迟数据意味着、用户在你的产品里点击按钮后、要等大约 1 秒才看到反应（人眨一次眼大约 100ms）"

**自检**：写完一段、用嘴轻读出来——卡在哪里就改哪里。书面语和口语之间的距离、就是 AI 文和人文之间的距离。

**反例参照**：维基百科开头那种"X 是 Y 领域的一个 Z、由 A 在 B 时间提出、用于 C 场景"。这是合规的百科风、不是判断交付型报告的风。判断交付型报告应该开门见山——"X 在 Y 场景里值得用、因为 Z"——然后再展开。

### 反信任侵蚀

以下措辞看似谦虚，实际上会侵蚀用户对报告的信任。禁止使用：

- "以上内容可能已过时"——标注截至日期让用户自己判断，不替他做判断
- "仅供参考，不构成任何建议"——如果证据充分就给建议，如果不充分就说证据不足，不用免责声明逃避
- "我们会持续更新"——你做不到持续更新，不做空头承诺
- "本研究全面调研了……"——空泛的自我肯定，删掉

### 类比强制（用熟悉物压术语）

**读者首次遇到的每个抽象术语，必须配一个他熟悉的参照物。** 专业术语独立陈述、对懂行的读者是常识、对不懂的读者只是几个陌生字。类比把术语锚到读者已有的认知上，让他不必读完整份报告才慢慢学懂——这是 P5 原则的落地动作。

**实操**：

- 抽象术语首次出现时、紧跟一句 `约等于 / 相当于 / 类似 / 量级和... 差不多` 的对比说明
- 参照物必须是**目标读者**（phase 1 已确认的读者画像）熟悉的东西——给 PM 看的报告用 SaaS 产品做参照、给医生看的报告用临床指标做参照、给普通用户看的报告用日常物件做参照。同一个术语对不同读者要换不同参照
- 数量级要先压：`100 亿美元市值` 抽象 → `100 亿美元市值（A 股大概一家中型保险公司的体量）` 具体；`100ms 延迟` 抽象 → `100ms 延迟（人眨一次眼大约 100-150ms）` 具体
- 一个术语只压一次。后续出现时直接用术语即可、不要每段都重复类比

**对照举例**（以下仅示范类比的形式，不是可直接复制的内容；写报告时按本领域真实数据重新计算）：

| 抽象术语（独用） | 加熟悉物（推荐） |
|---|---|
| 北大核心 | 北大核心（约等于 SJR Q3-Q4 的中文版） |
| Embedding 维度 1024 | Embedding 维度 1024（约是 OpenAI text-embedding-3-large 的一半） |
| 100 亿美元市值 | 100 亿美元市值（A 股大概一家中型保险公司的体量） |
| 100ms 延迟 | 100ms 延迟（人眨一次眼大约 100-150ms） |
| LLM 上下文 1M token | LLM 上下文 1M token（约 75 万汉字、相当于 4-5 本《红楼梦》正文） |

zh-academic agent 文档已经在用这种实践（"约等于 SJR Q3-Q4 的中文版" 把中文核心目录映射到英文读者熟悉的指标）——phase 4 写作时把这种模式扩展到所有抽象术语。

**自检方法**：写完一段、把段落里的每个专业术语圈出来、对每个问 "目标读者第一次见到这个词时是不是立刻知道它的量级和性质？" 不知道的、加一句对比说明。

**例外**：术语本身就是读者关心的研究对象（如 phase 1 用户问 "什么是 Diffusion Model"、整篇报告就是在解释这个）——整篇报告就是它的 "类比"、不需要再单独加对比说明。

### 章节标题论点化（BCG Action Title）

**每个 H2 / H3 标题必须是一个可以独立成立的判断，不是话题标签。** 描述性标题（"市场分析"、"竞争格局"、"用户画像"）禁止；论点化标题（"市场已向腰部公司集中"、"竞争壁垒已从产品转移到分销渠道"、"Z 世代付费意愿集中在创意工具"）必须。

**自检方法**：标题写完后，在前面加"我认为"再读一遍。"我认为市场已向腰部公司集中"——成立、是论点；"我认为市场分析"——读不通、是话题标签。读不通就改。

**对照举例**：

| 描述性（禁止） | 论点化（推荐） |
|---|---|
| 市场分析 | 市场已向腰部公司集中、头部份额三年内将被切走 |
| 竞争格局 | 竞争壁垒已从产品转移到分销渠道 |
| 用户画像 | Z 世代付费意愿高度集中在创意工具、对工具型 AI 反感 |
| 未来趋势 | AI Agent 三年内不会替代 PM、但会重构 PM 的工作配比 |
| 行业现状 | 行业进入存量博弈、增长靠抢竞品份额而非新需求 |
| 启示 / 建议 / 总结 | 对你的产品决策的三个具体动作 |

**保留段名白名单**（不强制论点化、是结构性段名，validate 不会拦截）：`TL;DR` / `关键假设与翻盘条件` / `矛盾、不确定性与未覆盖维度` / `主线复述与回扣` / `引用来源`。旧版段名 `矛盾与不确定性` / `待补研究` 不在 validate 黑名单里、跑历史报告不会触发，但写新报告应使用新段名。

**validate 硬阻断**：精确等于以下任一描述性短语的 H2 / H3 直接 fail——`市场分析` / `竞争格局` / `用户画像` / `行业现状` / `未来趋势` / `发展现状` / `总体概述` / `主要挑战` / `应对策略` / `核心要点` / `关键发现` / `研究背景` / `问题描述` / `解决方案` / `建议措施` / `总结展望` / `概览` / `现状` / `趋势` / `展望` / `总结` / `综述` / `讨论` / `分析` / `概述`。这是最经典的描述性话题标签，不在此列的描述性标题（如"对你的 X 的启示"）validate 不会硬拦，但写作时仍按本节规则自检。

### AI 文风黑名单（validate 软警告）

AI 生成的文字有一组高度可识别的"AI 痕迹"。这些词或句式单独出现可能没问题、但**密集出现**就是 AI slop 的明显信号。下面分三类列出，写作时主动避开；validate 命中会**报警告**（不阻断验证通过、但应人工复查并决定是否修改）。

**中文 AI 词汇**（最高频）：

- 程式化收尾：`值得注意的是` / `综上所述` / `由此可见` / `总而言之` / `显而易见`
- 浮夸词：`不容忽视` / `举足轻重` / `至关重要` / `独树一帜` / `日新月异` / `百花齐放` / `如火如荼`
- 商业空话：`深度赋能` / `保驾护航` / `全面提升` / `显著提升`
- 含糊归因：`行业报告显示` / `有观察人士认为` / `相关人士透露` / `业内分析人士`

**英文 AI 词汇**（即使在中文报告里出现也是 AI 痕迹）：

- 高频 AI 词：`Additionally` / `delve` / `intricate` / `pivotal` / `tapestry` / `testament` / `underscore` / `vibrant`
- 中后期 AI 词：`fostering` / `highlighting` / `showcasing`
- 推销词：`boasts` / `nestled` / `profound` / `groundbreaking` / `renowned`

**句子层模式**：

- 否定式平行：`不仅 X，而且 Y` / `不只是 X，更是 Y` / `Not just X, but also Y`——这种句式制造"我在纠正一个误解"的虚假姿态，多数情况下直接说 "X 是 Y" 更有力
- "尽管 X 但 Y" 模板收尾：`尽管面临挑战，但前景广阔`——AI 报告标志性的虚假平衡

**为什么是软警告而非硬阻断**：上述很多词在特定场景下确实合用（比如 SEC 文件原文里 `profound impact` 是法律术语、引用医保规则原文里 `至关重要` 是政策措辞），不能一棒打死。validate 报警告让你看到"这里可能有 AI 痕迹"，由你判断是 LLM 在套模板还是真的需要这个词。

**自检方法**：写完一段后，把段落里出现的每一个上述词都过一遍——问自己 "如果不用这个词、用大白话说，意思有损失吗？" 没损失就改成大白话。

**警告处理纪律**：validate 输出的 `! AI 文风：...` 警告**必须人工过一遍**——对每条命中段落自行判断是不是真的在套 AI 模板，是就改、不是就留。不允许"既然不阻断就全部忽略"的态度——这条规则失守，本节就退化成摆设。

### 语言纯度（硬约束）

**所有可以用中文表达的概念必须用中文**。模型默认会把英文行话当专有名词保留——`context`、`sub-agent`、`cache miss`、`verification`、`workflow`、`playbook` 这些词在中文里都有公认对应词、保留英文是无意识跟着英文素材走、不是判断结果。

**为什么是硬约束**：phase 2 / 3 抓的资料以英文为主、AI 圈语料也偏英文、模型在 phase 4 写中文时注意力会被英文素材拉偏。不在这一步显式拦截、产出报告必然中英夹杂——读者要一边读中文一边在脑里做英汉切换、阅读流畅度直线下降。这是给中文读者的报告、不是 AI 圈内部交流。

**因为你正在被英文素材拉偏、所以下面这张表的判断顺序不能颠倒、也不能跳过——它是给你的注意力补外挂。**

**路由表**——每个英文词进入报告前、按以下顺序匹配豁免类、匹配不到 1-8 行的必须按第 9 行翻成中文。**第 9 行是封口规则、所有落在 1-8 行之外的英文片段都走这一条、没有第三态**：

| # | 类别 | 处理 | 例子 |
|---|------|------|------|
| 1 | 公司名 / 产品名 / 人名 / 机构 | 保留原文 | OpenAI、Cursor、Anthropic、月之暗面、Ryan Lopopolo |
| 2 | 模型名 / 版本号 | 保留原文 | Claude Opus 4、GPT-5、Kimi K2.6、Qwen3-Coder |

| 4 | benchmark 名 / 度量单位 / 数据格式 | 保留原文 | SWE-bench、HLE、USD/MTok、token、JSON、JSONL |
| 5 | 通用计算与互联网术语缩写（**白名单**） | 首次出现写"中文译名（缩写）"、后续可只用缩写 | **白名单（仅这些走第 5 行）**：API、SDK、MCP、CLI、IDE、URL、DOI、HTTP、JSON、CSV、SQL、GPU、CPU、RAM。**白名单之外的 AI 子领域缩写**（如 KV-cache、CoT、RLHF、RAG、ReAct、MoE、PPO、DPO、SAE、SFT）**不走第 5 行、走第 6 行**——查 `known_terms` |

**违规形状示例**——下面的清单只是给你看违规长什么样、**不是穷举黑名单**。判断流程仍然是路由表——先匹配 1-8 行、不匹配就翻、**不要回头查清单是否含此词**：

- 概念词例：context（上下文）、framework（框架）、architecture（架构）……及所有同类抽象名词

- 工程词例：cache（缓存）、sandbox（沙箱）、workflow（工作流）、playbook（操作手册）、benchmark（基准测试）、prompt（提示词）……及所有同类工程概念
- 状态词例：trace（轨迹）、log（日志）、session（会话）、thread（线程）……及所有同类运行时状态

**好坏对比**：

例 1（普通行话——最常见的违规类型）：
- ✗ Manus 那篇文章是 context engineering 这个领域的奠基文献、6 条铁律来自 4 次重写 agent 框架的代价。
- ✓ Manus 那篇文章是上下文工程领域的奠基文献、6 条铁律来自 4 次重写 agent 框架（agent 命中第 6 行 known_terms、保留）的代价。

例 2（动作词 + 角色词 + 状态词）：
- ✗ Anthropic 把 verification 三类按可靠性排序：rules-based feedback 最稳、visual feedback 次之、LLM-as-judge 最弱。
- ✓ Anthropic 把验证手段按可靠性排序：基于规则的反馈（如 lint、tests）最稳、视觉反馈（截图、渲染结果）次之、用 LLM 当裁判最弱。

例 3（缩写处理——首次给全称、后续可只用缩写）：
- ✗ MCP 把所有可用 tools 的 schema 在 session 开始时注入 context、agent 不论用不用都得带着。
- ✓ Model Context Protocol（MCP）把所有可用工具的 schema 在会话开始时注入上下文、agent 不论用不用都得带着。

例 4（整段英文引用必须配紧邻翻译）：
- ✗ Lopopolo 在访谈里说："I'm pretty bearish on [MCP] because the harness forcibly injects all those tokens in the context, and I don't really get a say over it."
- ✓ Lopopolo 在访谈里说："I'm pretty bearish on [MCP] because the harness forcibly injects all those tokens in the context, and I don't really get a say over it."（"我对 MCP 比较悲观、因为 harness 强行把所有 token 注入上下文、我没有发言权。"）

例 5（核心英文术语——首次释义、后续直用）：
- 假设 user_profile.json `known_terms` 含 "harness"
- **"首次"的精确定义**：该报告 markdown 文件中按行号顺序**第一次出现**的位置。不算 phase 1-3 的对话历史、不算其他报告、不算这份 phase4 文档里的示例
- 报告首次出现：✓ "agent harness（承载层）已成为产品差异化主战场"
- 后续段落：✓ "harness 工程化"、"跨模型 harness"——不再重复释义
- 边界：harness 在 H2 段 A 出现 5 次、又在 H2 段 B 出现 3 次 → 按全文首次算（在段 A 第一次出现位置配释义即可、段 A 后 4 次和段 B 全部 3 次都不重复）

**与「类比强制」节的关系**：「类比强制」处理"读者不熟悉的术语首次出现要配类比"、本节处理"凡是有中文译名的英文词必须用中文"。两节正交不重复——前者管理解门槛、后者管语言纯度。两节顺序明确：先决定语言形式（路由表）、再决定要不要加类比。

**自检方法（段内执行、不堆到事后）**：

**每写完一个 H2 段、立即把该段所有连续英文片段圈出来（不含明显属于 1-4 行豁免类的、如公司名 / 产品名 / 文件名）、对每个问"匹配路由表第几行？"。匹配不到 1-8 行的当场翻成中文、再写下一段。不允许把语言纯度自检堆到整篇报告写完之后。**

理由：写完 5000 字报告后注意力已耗尽、事后扫描多半流于形式（要么跳过、要么扫一眼说"看起来都符合"）。段内自检的成本低（单段英文片段数有限）、判断准（注意力还在该段写作上下文中）、错了影响小（一段错只改一段）。

报告整体写完后、再跑 validate 脚本看 `! 语言纯度` 警告作为兜底——脚本扫的是高频违规模式、不可能穷举、人工段内自检仍是主负责。

**警告处理纪律**：validate 输出的 `! 语言纯度：...` 警告**必须人工过一遍**——按警告中给的位置确认是真违规就翻、是合理豁免（如该词在 `known_terms` 里）就保留并继续。"既然不阻断就全部忽略"的态度会让本节退化成摆设。

| `user_profile.json` 字段 | phase 4 怎么用 |
|---|---|
| `user_role` | 报告语气、举例、参考物（PM 用 SaaS 产品做参照、医生用临床指标做参照） |
| `user_expertise_level` | `unfamiliar` → 大量类比 + 背景铺垫；`basic` → 关键术语配类比 + 跳过常识；`proficient` → 直接进专业讨论、保留必要类比；`expert` → 跳过基础解释、要看到他不知道的细节 |
| `decision_context` | 「主线复述与回扣」段**最后一句必须**接回这个具体决策。例：`decision_context = "决定是否把团队代码补全工具从 Copilot 切换到 Cursor"` → 主线复述末句"基于上述判断、你的团队应该 {X}"、**禁止**写成"AI 编程工具市场仍在演进"这种泛泛回扣 |
| `key_concerns` | 「详细分析」段必须按 key_concerns 的**顺序和优先级**组织——不能用别的逻辑切片（如不能按"市场 / 技术 / 政策"三段式平铺、必须按用户最关心的子问题逐个回答） |
| `known_terms` | 这些术语在报告中**省略**类比解释（用户已经懂、再解释是浪费篇幅 + 显得居高临下） |
| `unfamiliar_terms` | 这些术语**首次出现**时必须配类比解释（参见本文档「类比强制」节）。`unfamiliar_terms` 中术语首次出现时未配类比 → 视同违反「类比强制」节硬约束 |
| `constraints` | 报告中必须**逐条回应**——例 `constraints = ["预算 1 万以内"、"3 月底前出结果"]` → 报告必须出现"在你的预算范围内 A 方案最合适" + "在你的截止日前 B 方案是唯一可行的"。回应可以集中在「核心结论」、可以分散在「详细分析」、但每条 constraint 都要被显式回应至少一次 |
| `avoid_topics` | 这些方向**不出现在报告中**——出现说明 phase 4 没读 user_profile.json |

### 自检

phase 4 写完报告、做以下硬检查：

- 「主线复述与回扣」段最后一句是否接回 `decision_context` 的具体动作？没有 → 重写
- `constraints` 数组每条是否都在报告中找到至少一次显式回应？没找到 → 补回应
- `unfamiliar_terms` 数组每个术语在报告中首次出现的位置是否配了类比？没配 → 补类比
- `avoid_topics` 数组每条对应的方向是否在报告中**没出现**？出现 → 删掉

### 禁止

- "基于你的背景……" 后面跟一段通用模板。`user_profile.json` 字段要被**实际用上**、不是开头列一遍当摆设
- 把 `user_profile.json` 的所有字段罗列在报告开头——那是你的笔记、不是给读者的内容
- `decision_context` 字段为空就跳过 `## 主线复述与回扣` 段——这种情况说明 phase 1 没完成、回退到 phase 1 重做（见 SKILL.md 「反向回滚机制」段）

**为什么是硬约束**：报告写得越长、phase 1 的具体语境越容易被淡忘。LLM 进入 phase 4 时陷入"完成报告骨架"的惯性、忘记 phase 1 那个具体的人在等什么答案。schema 调用让 phase 4 在写每个段落时都要**显式查 user_profile 字段**——校对成机械动作、phase 1 的工作不再依靠 LLM 自觉。

## 中文报告的特殊适配

中文和英文的阅读习惯不同，报告需要针对性调整。

**并列论点用分项编号。** 中文段落里 3 个及以上的并列陈述容易被跳读——读者扫一眼就跳到下一段。用编号（1. 2. 3.）强制逐项对齐。2 个及以下的并列项可用段落行文，不需要编号。这来自腾讯较真等中文事实核查平台的实践。

**"弱推荐"必须加括注。** 中文语境中"弱推荐"容易被误读为"这个建议不太行"。必须在后面加括注说明——"条件性推荐（证据确定性低：仅基于观察性研究，尚无随机对照试验验证）"。

**涉及中国药品审评时用 CDE 三元判据。** 如果研究涉及中国境内药品上市审评，负面结论按"安全性 / 有效性 / 质量可控性"三个维度分别陈述，这是中国药品审评中心（CDE）的标准审评维度。其他医疗场景根据具体问题选择合适的分析维度。

**英文原文证据保留原文。** 引用英文来源的关键证据时，保留英文原文并附中文翻译对照，不只给翻译版——用户可能需要看原文判断翻译是否准确。

- **时效敏感结论**在段落末标注数据日期："（数据截至 2025-Q3 [5]）"

- **监管/政策类信息**标注具体的文件编号和发布日期

## 引用纪律

- **引用跟事实走**——强主张（定价数字、版本号、技术规格、原文引语）在句中事实后紧跟 `[N]`；通用论述、综合判断在段末统一收尾 `[1][2][3]`
- **多源必须独立角标** `[1][2][3]`。NEVER 写成 `[1,2,3]`、`[1-3]`、`[1、2、3]`——viewer 正则只匹配单个数字方括号
- **角标在句号前**：`陈述 [3]。` 引语角标在右引号外：`"原文" [3]`
- **引用即可查**——正文中每个 [N] 在 sources.json 中有完整条目
- **零容忍**——不允许占位符（`[?]`）、编号跳跃
- NEVER 根据记忆或推测编造 URL、DOI、论文标题。搜索不到就标注"未能找到原始来源"，不伪造引用
- NEVER 在正文中直接写裸 URL（如 `example.com/path`）。viewer 的 `linkify` 会把它转成可点击链接，和旁边的引用角标视觉混淆。所有 URL 一律放在 sources.json 中，正文只用 `[N]` 角标指向它
- **`[unverified]` 标记**——phase 3.5 中 `degrade_action = mark_unverified` 的 claim 在角标后追加 `[unverified]` 标记。例：`Lambert 指出 LLM 无法区分新发现和错误[12][unverified]`。该标记**不计入 sources.json 校验**（unverified 不等于无来源、只是 NLI 没判断 entail），但读者一眼能看到该陈述的核查强度被降级

## claims.json 取值与 grounding 自检（phase 3.5 衔接硬约束）

phase 3.5 已经把所有强核查项写入 `claims.json`、附带 grounding 判断结果与 `degrade_action`。phase 4 写作时**所有数字 / 日期 / 人名 / 公司关系 / 引文 / URL / YMYL 结论**必须按 `claim_id` 从 `claims.json` 取值、**不允许 LLM 自己生成或临场推理**——这条是 hallucination 防御的硬路径。

### 取值规则

- 写到任何强核查项时、先在 `claims.json` 里找对应的 `claim_id`、复制 `claim_text` 字段值（如果是 `soft_degrade` 则改用 `degrade_phrasing` 字段值）到正文
- 该 claim 关联的 `source_ids` 数组直接转成正文角标 `[n][m]`
- claim 在 phase 3 结论里没出现过（即 `claims.json` 没收录）→ 不允许 phase 4 临场新增数字 / 人名 / 引文。要么回 phase 3 重新做、要么从报告中移除该陈述
- `degrade_action` 决定取值方式：

| degrade_action | phase 4 行为 |
|---|---|
| `multi-source` 或 `single-source`（无降级） | 直接用 `claim_text` 原文 + 角标 |
| `soft_degrade` | 改用 `degrade_phrasing` 字段的措辞模板（自带"据 X 报道、截至 Y 日尚未官方确认"句式） |
| `mark_unverified` | 用 `claim_text` + 角标后追加 `[unverified]` 标记 |
| `drop` | 不出现在报告中 |
| `hard_fail` | 不应出现——hard_fail 在 phase 3.5 已被处理（要么升级、要么移除）。如果 phase 4 看到 hard_fail 状态的 claim、说明 phase 3.5 没完成、回退到 phase 3.5 重做 |

### 段落写完后的轻量自检

每写完一段（H2 或 H3 之内的连续段落组）、对该段做一次轻量自检：

1. 把段落里所有强核查项（数字 / 日期 / 人名 / 公司关系 / 引文）圈出来
2. 对每个圈出的项、确认它在 `claims.json` 里有对应 `claim_id`（不允许 phase 4 凭空写）
3. 对应 claim 的 `degrade_action` 决定的取值方式（见上表）是否被正确应用——例如 `mark_unverified` 的 claim 角标后是否带了 `[unverified]`

**Haiku 协助自检**：把段落 + 段落涉及的 claims 子集喂给 Haiku、问 "这段是 supported / unsupported / partially supported"。判断为 `unsupported` 或 `partially supported` 的段落 → 触发 rewrite。

### unsupported 段落的 rewrite 流程

- 第 1 次 rewrite：删除段中无 `claim_id` 支撑的内容、只保留有 grounding 的部分；再跑一次自检
- 第 2 次 rewrite：仍 unsupported → 把段落涉及的所有强核查项标 `[unverified]` 角标、明确告诉读者"以下陈述未被 phase 3.5 grounding 通过"
- 超过 2 次仍 unsupported → 该段保留 `[unverified]` 标记、进入"开头 metadata grounding 强度"统计的 U 计数

**为什么有上限**：Rewrite 无限循环说明 phase 3 结论本身可能存在 hallucination、不是 phase 4 写作问题——上限触发后回退到 phase 3 重做（见 SKILL.md 「反向回滚机制」段）。

报告按章节（H2 段落）渐进生成，写完一个章节再写下一个。每个章节写完后校验该章节内的引用编号是否在 sources.json 中有对应条目，发现缺失立即补上。不设章节字数上限。

## Viewer 格式契约（硬约束）

报告由配套 viewer 网页渲染（viewer 代码位于 `VIEWER_DIR`）。以下规则对应 viewer 的解析逻辑，违反会导致渲染失败或视觉混乱。

### 文档骨架

1. 唯一一个 `# H1` 是报告标题。
2. 标题后紧跟 metadata 引用块，**只允许以下两个字段，不允许添加任何其他字段**：
   ```
   > 来源数量：{N} 个
   >
   > 截至日期：{YYYY-MM-DD}
   ```
   两个字段之间必须有一个空的 `>` 行，确保 viewer 渲染时各占一行。
   NEVER 添加"研究深度""研究范围""研究主题""评估总览"等额外字段。
3. `## TL;DR` 必须是正文第一个 H2。
4. 后续 `##` 章节按内容自然组织。**禁止**在标题中带手工编号（如 `§1`、`一、`、`1.`）——viewer 的 TOC 自动从 H2/H3/H4 抽取目录。
5. **H2 / H3 章节标题必须论点化（BCG Action Title）**——每个标题都是一个可以独立成立的判断，不是话题标签。详细规则见下文「写作纪律」段「章节标题论点化」一节。不用中英混杂术语。
6. markdown 末尾**必须**写 `## 引用来源` 段——按 num 升序逐条列出，每条用 `[N] {标题} — {YYYY-MM-DD} — {T1/T2/T3} — {URL}` 格式独立成行，字段间用全角破折号 `—` 分隔。如果 title 自带机构名（如 "McKinsey: ..." / "WHO Report on ..."），机构信息已在 title 里、不再单列。这一段的存在是为了让 markdown 文件脱离 viewer 也是自洽文档（用户用 typora、vscode、github 网页等 raw markdown 阅读器打开时能查到每个角标的来源）。viewer 渲染时会自动检测并移除这一段，用 sources.json 的富展示版本（带 tier 标签、原文摘录 hover）替代——同一份报告 raw md 看到一个版本、viewer 看到另一个，两者编号集合必须完全一致。
7. **禁止**文档末尾的"自我标识"括号行。

### sources.json

与报告同名的 `.sources.json` 文件并列输出到 `REPORTS_DIR`。viewer 从中读取来源数据渲染弹窗和底部引用列表。

**文件结构必须是**：`{"sources": [...]}` —— 一个对象，`sources` 键包含来源数组。NEVER 输出裸数组 `[...]`。

**viewer 强契约字段（6 个，全部必需）**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `num` | int | 与正文 `[N]` 严格对齐，连续编号从 1 开始 |
| `title` | string | 来源标题 |
| `url` | string | 完整 URL |
| `date` | string | `YYYY-MM-DD` 或 `YYYY-MM` |
| `authority_tier` | string | `T1` / `T2` / `T3` |
| `evidence_quote` | string | ≤200 字原文摘录 |

**一致性硬约束**：正文每个 `[N]` 必须在 sources.json 有对应条目，反之亦然。

**sources.json 缺失时**：markdown 自带的 `## 引用来源` 段（见上文「文档骨架」第 6 条）本来就是硬性要求——sources.json 缺失时 validate 会因"缺少 sources.json"报错，但报告本身的引用信息不会丢，用户仍可从 markdown 自带段查到每个角标的来源。

### 标点纪律

- 句号、逗号、顿号正常使用。**禁止**用 `·`（中点）替代标点。
- `·` 只允许两处：标题分隔（`AI Coding Agent · 2026 年 4 月`）、并列实体（`Cursor · Claude Code · Cline`）。

### 报告交付流程

报告完成后必须严格执行以下步骤，不可跳过。

**步骤 1 · 命名与写入**

报告文件名：`{主题关键词}-{YYYY-MM}.md`（全小写、连字符分隔、英文）。
来源文件名：与报告同名但后缀为 `.sources.json`。
两个文件都写入 `REPORTS_DIR`（即本 skill 目录下的 `reports/` 子目录、详见 SKILL.md「路径约定」段、绝对路径形如 `~/.claude/skills/deeeeep-research/reports/`）。如果 `reports/` 目录不存在，写入前自动创建。

**步骤 2 · 程序化格式验证**

报告和 sources.json 写入后，运行验证脚本：

```bash
py ~/.claude/skills/deeeeep-research/viewer/validate_report.py ~/.claude/skills/deeeeep-research/reports/{文件名}.md
```

`~/.claude/skills/deeeeep-research/reports/` 是 skill 自带的 `REPORTS_DIR`、详见 SKILL.md「路径约定」段。

脚本检查（错误，阻断通过）：metadata 字段是否只有规定的两个、H1 是否唯一、第一个 H2 是否为 TL;DR、标题是否有手工编号、章节标题是否为描述性话题标签、角标格式是否正确（禁止逗号/连字符连写）、正文是否有裸 URL、sources.json 格式是否为 `{"sources": [...]}`、6 个必需字段是否齐全、正文角标和 sources.json 编号是否一一对应、markdown 末尾是否有 `## 引用来源` 段且段内 [N] 编号集合等于正文角标集合。

脚本另外**报警告**（不阻断通过、应人工复查）：**AI 文风黑名单命中**（中文 AI 词汇 / 英文 AI 词汇 / 否定式平行 / "尽管 X 但 Y" 收尾模板）。

脚本输出 `OK 格式验证通过` 或 `OK 格式验证通过（含警告）` 才能进入步骤 3。输出错误（前缀 `x`）则按错误提示逐项修正，修正后重新运行脚本，直到通过。警告（前缀 `!`）不阻断通过，但**必须人工过一遍**——对每条命中段落自行判断是不是真的在套 AI 模板，是就改、不是就留。详见上文「写作纪律」段「AI 文风黑名单」一节的「警告处理纪律」。

**phase 3.5 grounding 检查（同一脚本同时做）**：与报告同名的 `.claims.json` 文件（如 `xxx.claims.json`）若存在、脚本会校验 10 字段 schema 完整性 + 不允许 `hard_fail` 状态进入 phase 4（错误）+ `mark_unverified` 数量统计（警告、应在报告 metadata 的 `grounding 强度` 行显示）。`.claims.json` 缺失时：未运行过 phase 3.5 的旧报告允许通过、但 phase 3.5 落地后的新报告必须有该文件、否则报错。

**步骤 3 · 环境检测 + 交付链接**

交付链接前，先确认 viewer 服务在跑：

```bash
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8765/viewer/
```

- 返回 `200` → 服务正常，直接进入交付
- 返回其他或不可达 → 用 `py` 命令启动服务（serve.py 位于 `VIEWER_DIR`、不带参数运行即可、默认会扫 skill 自带的 `reports/` 目录）：
  ```bash
  py ~/.claude/skills/deeeeep-research/viewer/serve.py &>/dev/null &
  ```
  等待 3 秒后重新检测。最多重试 3 次（每次间隔 3 秒）。3 次后仍不通过 → 向用户报告"viewer 服务启动失败"、同时附上报告文件路径让用户手动查看。

  **关键纪律**：检测到端口 8765 已被占用、不要复用旧实例——旧实例可能绑定的不是 skill 自带 reports/ 目录、会导致刚生成的报告扫不到。先用 `taskkill //PID <pid> //F`（Windows）或 `kill <pid>`（unix）杀掉旧进程、再用上面命令重启、确保新实例绑定的是 skill 自带 reports/。检测端口占用进程：`netstat -ano | grep :8765`（Windows）/ `lsof -i :8765`（unix）。

环境就绪后、向用户输出以下两行（每次都必须输出、格式固定）：

```
报告文件：file:///~/.claude/skills/deeeeep-research/reports/{文件名}.md
在线查看：http://127.0.0.1:8765/viewer/?report={文件名不含.md}
```

报告文件路径用 skill 自带的绝对路径（Windows 下展开 `~` 为 `C:/Users/{username}/`、用正斜杠）。所有路径都指向 skill 自带 `reports/` 目录、与外部工作目录无关。

NEVER 省略这两个链接。NEVER 只给其中一个。这是用户判断报告是否成功入库的唯一凭据。
NEVER 输出"服务可能未启动"之类的猜测——要么确认服务在跑，要么自己启动它。
